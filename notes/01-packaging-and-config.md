# OpSkills packaging and configuration

How OpSkills is installed, configured and run.

## Goals

- One self-contained binary, `opskills`, with no runtime dependencies (no JVM, no interpreter).
- Docker image under 30 MB compressed. Memory at idle under 50 MB.
- Ready to serve within 2 seconds of start.
- Secure on first start, with no well-known passwords or keys.

## Deliverables

| Artifact | Contents | Built with |
|---|---|---|
| `opskills_<version>_<arch>.deb` | Binary, systemd unit, default config, man page | `cargo-deb` |
| `ghcr.io/opskills-app/opskills:<version>` | Binary on a distroless or scratch base, multi-arch (amd64, arm64) | Multi-stage Dockerfile |
| `opskills-<version>-<target>.tar.gz` | Binary only, for other platforms | GitHub Actions release |

## Filesystem layout (Debian package)

| Path | Purpose | Mode |
|---|---|---|
| `/usr/bin/opskills` | The binary | 0755 |
| `/etc/opskills/opskills.toml` | Main config (conffile) | 0640, `root:opskills` |
| `/var/lib/opskills/` | Data dir: SQLite database, encryption key, server identity | 0750, `opskills:opskills` |
| `/var/lib/opskills/plugins/` | Installed plugins | 0750 |
| `/lib/systemd/system/opskills.service` | Service unit | 0644 |

Logs go to stdout as structured JSON, so journald (deb) or the container runtime collects them. No log files are written by default.

## Install scripts

- `postinst`: create the `opskills` system user and group if missing, create the data dir, run `systemctl daemon-reload`, and enable the service (without starting it on first install).
- `prerm`: stop the service.
- `postrm purge`: remove the data dir and the system user.
- No secrets are generated by install scripts. The server generates them on first start (see below), which works the same way in the package and the container.

## systemd unit

Runs as `opskills:opskills` with sandboxing: `NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`, `ReadWritePaths=/var/lib/opskills`, `CapabilityBoundingSet=` (empty), and `Restart=on-failure`.

## First start

On first start, if missing, the server creates these in the data dir:

| Item | How | Stored as |
|---|---|---|
| Server ID | Random UUID v7 | `server-id`, 0600 |
| Secret-encryption key | 256 random bits | `master.key`, 0600 |
| Admin account | Random 24-character password | Hashed with Argon2id in the database; the plaintext is printed once to the log with a clear banner |

Each container or host therefore gets its own identity, key and password. A cluster shares identity through the database, not through a fixed default.

## Configuration

One file, `opskills.toml`. Every key can be overridden by an environment variable: `OPSKILLS_` plus the key path in upper case, with `__` between levels.

```toml
[server]
listen = "0.0.0.0:8080"
public_url = "https://ops.example.com"

[database]
url = "sqlite:///var/lib/opskills/opskills.db"   # or postgres://...

[auth]
session_timeout = "8h"
api_token_max_lifetime = "90d"
proxy_auth = { enabled = false, user_header = "X-Forwarded-User", groups_header = "X-Forwarded-Groups" }

[logs]
format = "json"     # or "pretty"
level = "info"

[runs]
retention_days = 60
min_runs_to_keep = 50
```

Example override: `OPSKILLS_DATABASE__URL=postgres://...`.

Rules:
- No templating tool at container start. The binary reads the file and the environment directly.
- Secrets can be given as `*_file` keys (for example `database.password_file`) so they can come from Docker or Kubernetes secrets instead of environment variables.
- After loading config, the server removes `OPSKILLS_*` variables from the environment it passes to anything it runs, so secrets never leak into runbook steps.
- `opskills config check` validates the file and prints the effective config with secrets masked.

## Container image

- Base: distroless static (or scratch plus CA certificates and tzdata).
- Runs as a non-root UID. Works with arbitrary UIDs (no `/etc/passwd` rewriting needed).
- `EXPOSE 8080`. One volume: `/var/lib/opskills`.
- `HEALTHCHECK` uses `opskills healthcheck`, which calls `/healthz` on the local server.
- PID 1 is the binary itself. It handles SIGTERM, drains running steps, and exits cleanly.

## Authentication options

- Built-in users (Argon2id password hashes).
- OIDC single sign-on.
- Trusted reverse proxy that sends user and group headers (off by default).
- API tokens with a maximum lifetime, scoped to a workspace and a role.
